# 当前结论

企业 Agent 的最小产品单元不应是一个泛化聊天入口或“能力平台”，而应是一段边界明确、已有成本、结果可验收、可以人工接管的工作。优先选择高频、耗人或漏掉就损失收入、成功标准清楚、可接入现有系统且预算所有者明确的 workflow，再从辅助、分流、协调或受限动作逐步扩大授权。

# 判断依据

瓴羊访谈把企业客户的购买对象从软件功能改写为能承担运营、营销、客服或销售指标的“AI 员工”；Greg Isenberg 的播客整理用“SaaS 卖软件，Agent SaaS 卖工作”表达相同方向。两篇来源都强调客户最终按更快、更好、更省或增长结果判断价值，而不是按模型和界面的新颖度判断。

知识库接受“以工作结果定义产品”的核心，但不把“AI 员工”当作已经实现岗位自治的事实。真正的产品边界还包括触发条件、上下文、工具、权限、批准点、转人工规则、失败补救和成功口径；缺少这些条件，“卖结果”容易退化成营销承诺。

两篇来源在场景筛选上互相强化：企业已经为人力、外包、漏单或重复协调付费；任务高频且规模足够大；完成标准能被观察；模型可以访问所需数据和系统；错误风险能通过审批、限额或升级控制。

本次没有独立验证客户 ROI、准确率、定价或采用率。两篇来源来自同一媒体体系，且一篇是厂商访谈、一篇是创业播客整理，因此置信度为 medium 而非 high。

# 应用方式

选择首个企业 Agent 场景时，先给候选工作打分：

1. 现有成本：是否已有工资、外包、漏单、等待或合规成本；
2. 频率与规模：是否每天重复，客户数量或单次价值是否足够；
3. 结束状态：能否清楚判断已完成、需复核或已失败；
4. 上下文与工具：数据能否合法访问，系统是否可稳定调用；
5. 风险边界：哪些动作可自主，哪些需审批、限额或转人工；
6. 预算与归因：谁付钱，价值如何与季节、渠道和人工贡献区分；
7. 可复制性：同一行业是否至少有多个客户共享相似流程。

首版优先采用四种形态：生成草案后由人批准、入口分类与分流、跨系统查询与协调、明确规则和限额内的小动作。只有这些路径在真实案例中稳定后，才扩大任务范围和自主权。

定价可从设置费、订阅、用量或活动周期开始。结果计费应等基线、归因、异常处理、质量下限和风险分配稳定后再引入，且不能只奖励短期转化。

# 适用边界

- 高度模糊、低频、一次性、不可逆或严重依赖伦理与关系判断的工作，不适合直接产品化为自主 Agent。
- 企业已经付费不代表 Agent 一定更便宜；集成、监督、错误补救和合规可能超过节省的人力。
- “AI 员工”可能掩盖幕后人工、FDE 和持续运营，应报告人工介入与真实总成本。
- 结果计费容易受归因争议、选择性服务和代理指标投机影响，需要质量与长期价值约束。
- 电话、会员、交易、退款等流程涉及隐私、身份、消费者告知和申诉机制。

# 不同观点与冲突

传统 SaaS 的存储、计算、权限、规则和界面不会因为 Agent 出现而消失；Agent 更可能成为新的操作层。部分客户仍希望购买工具并保留流程控制，而不是把责任外包给服务商。产品应根据客户成熟度提供建议、协作、托管等不同自治等级，不强迫单一“雇佣 AI 员工”模式。

# 我的认知

[新增] 接受“工作结果而非功能列表”作为企业 Agent 的产品定义，同时增加可接管、可归因、可复制和总成本约束，避免把意图、Demo 或厂商自报 ROI 当作业务结果。
