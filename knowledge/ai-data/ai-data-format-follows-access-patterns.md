# 当前结论

AI 数据底座不存在对所有 workload 都最优的单一格式。应根据数据模态、读写模式、结构演进、索引、版本治理和引擎生态选型：结构化分析继续优先使用成熟湖格式；当同一批多模态数据需要频繁加列、随机点查、混合对象访问、向量或全文检索以及实验版本管理时，再评估 Lance 一类 AI-native 格式作为补充。

# 判断依据

传统分析型湖格式主要优化批量扫描、列式分析、快照和多引擎治理。训练 shuffle、样本回放、检索命中后的原文取回、宽表特征增量和大对象访问，对随机行读取、低成本加列和对象定位提出了不同要求。

来源文章用 Lance 说明一种设计方向：把文件访问、表级版本、索引和目录协同组合成面向 AI workload 的格式栈。这能够减少跨对象存储、索引系统和元数据库之间的重复复制与一致性协调，但不等于所有能力必须由一个产品承载。

本次只核对了文章内部的架构叙述与适用边界，没有用官方规范、独立基准或生产用户材料验证 Lance 的具体性能与成熟度。

# 应用方式

数据平台选型时，先回答以下问题：

1. 数据是否包含图片、视频、点云、音频、Blob、embedding 等异构对象？
2. 主要读取模式是大批量扫描，还是按行随机访问、shuffle、样本回放和检索后取回？
3. 是否需要频繁增加标签、特征、embedding 或模型得分列，并避免重写历史数据？
4. 是否同时需要标量、向量和全文索引？
5. 是否需要用 Branch、Tag、快照或血缘管理实验、评测与发布？
6. 现有计算引擎、Catalog、权限、备份、监控和运维体系能否接入？

只有当新 workload 的收益能够覆盖格式转换、双写、治理和团队学习成本时，才进入 PoC。PoC 应至少比较 P95 随机读取延迟、批量吞吐、加列成本、重复存储比例、索引构建与更新成本、故障恢复和跨引擎兼容性。

# 适用边界

- 对纯结构化报表、离线聚合和成熟湖仓治理，Parquet、Iceberg、Delta 或 Paimon 可能更简单可靠。
- 把多种能力下沉到格式层会减少部分外围协调，也可能带来生态成熟度、迁移、调试、权限和运维风险。
- “统一数据”不等于强行使用单一物理格式；逻辑统一、元数据一致和可追溯也可以通过分层架构实现。
- 本节点不证明 Lance 已经达到特定性能或生产成熟度，也不构成选型结论。
- 技术演进较快，正式选型前需要重新核对当前版本、兼容矩阵、社区活跃度和基准测试。

# 不同观点与冲突

另一种合理架构是继续让对象存储、开放表格式、向量数据库和全文检索系统各自承担擅长的工作，通过元数据、事件和数据契约维持一致性。这会增加系统数量，却可能获得更成熟的独立扩缩容、权限治理和故障隔离。

当前证据不足以判断“能力下沉到格式层”和“专用系统组合”哪一种在具体业务中总体成本更低，应以实际 workload 和 PoC 结果决定。
