# 当前结论

Agent 长任务的可靠性上限，不只取决于基础模型能力，更取决于是否有清晰规格、可复用的 skills 与工具、可观测的中间状态、可信评估器，以及失败后的重试、分支和回退机制。运行时间变长只代表潜在任务范围扩大，不能单独证明自治性或交付可靠性。

进入企业生产环境时，还必须把真实数据与 Context、系统权限、审批与人工升级、运行日志和分阶段放量纳入同一个闭环。一个能在演示中完成任务的 Agent，不等于可以长期承担真实业务。

# 判断依据

来源对谈把长链路失败解释为两个相互强化的问题：模型逐步走出熟悉分布后，错误概率上升；工作流若缺少及时评估，偏差会在开环执行中继续累积。对谈给出的两个方向是用 skills 把有效的人类方法编码进执行路径，以及让多个 Agent 搜索不同路径、再由评估器筛选。

性能优化示例说明，skill 的价值不是增加一段背景文字，而是把“建立基线—修改—复测—扩大测试面—检查资源影响—继续迭代”变成模型可以执行和验证的流程。软件迁移示例则说明，原实现、测试和行为差异共同构成高密度规格。

本知识节点把上述观点进一步整理成闭环工程原则。这是知识库的系统化判断；本次只核对了文章正文的一致性，没有独立验证某个 Agent 能稳定运行数天或数周，也没有比较不同模型和编排框架的成功率。

两篇企业 Agent 来源从产品和交付侧强化了同一结论：先观察员工真实执行路径，写清触发器、上下文、工具、可自主动作、批准点、转人工条件和成功标准；再用历史案例评测、低风险试点、低峰运行和逐步放量进入生产。瓴羊案例还强调数据治理与老系统接入，但其效果数字来自供应商或采访陈述，本次未独立验证。

# 应用方式

设计长任务 Agent 时，至少检查五个环节：

1. 规格：目标、输入、输出、验收标准、禁止事项和资源边界是否明确；
2. 路径：高价值的人类方法是否被写成可执行 skill，而不是只提供抽象建议；
3. 状态：每个关键阶段是否有可观察产物、日志、检查点和可恢复状态；
4. 评估：能否用测试、基准、规则、对照样本或人工复核及时判断进展与偏航；
5. 恢复：失败后能否缩小问题、回退检查点、切换方案或升级给人，而不是无限续跑。

企业生产还应增加第六项检查：先在历史案例和沙箱中回归，再从低权限、低风险、低流量场景上线，观察错误与人工接管后逐步扩量。每次模型、prompt、Skill、工具或流程变更，都应绑定版本和回归集，并报告端到端成功率、人工接管率、错误补救成本、权限异常和业务结果。

评估长任务能力时，应同时报告任务范围、连续运行时长、人工介入次数、重试次数、最终验收结果和失败样本。只报告“跑了多久”会把资源消耗误当作任务完成度。

# 适用边界

- Skill 可能把 Agent 约束在过时或局部最优的路径上，需要版本、适用条件和效果回归。
- 多 Agent 搜索会增加成本和延迟，而且同源模型可能产生相关错误，数量不能替代独立性。
- 评估器本身可能误判；当评估器与真实目标不一致时，闭环会稳定优化错误指标。
- 创意、价值判断、跨组织协商等任务常缺少快速客观验收，不适合完全自动闭环。
- 涉及高风险外部动作时，即使技术评估通过，也应保留权限控制和人工确认。
- 审批和日志只能降低部分风险，不能替代身份校验、最小权限、隐私治理、故障隔离和责任界定。
- FDE 或人工运营能补齐长尾，但若经验无法沉淀为稳定产品能力，交付成本可能随客户数量近线性增长。

# 不同观点与冲突

更强的基础模型有时能显著减少提示、skill 和编排复杂度，过度工程化也会降低适应性。因此，闭环组件应由实际失败模式驱动，而不是为每个短任务都搭建重型多 Agent 系统。

来源对谈对长周期 Agent 能力较乐观，但没有提供可复现实验。本节点不接受“能长时间运行”等于“能稳定自治”的强结论。

# 我的认知

[强化] 将 Agent 能力继续理解为“系统如何持续约束、观测、评估和恢复”，并把企业生产所需的数据、系统接入、审批、日志和分阶段上线纳入闭环。长任务首先是可靠性工程问题；Demo、运行时长或厂商自报效果都不能单独证明交付可靠性。
